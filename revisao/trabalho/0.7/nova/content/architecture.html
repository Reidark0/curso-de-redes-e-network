Arquitetura

Em vez de um único protocolo resolver tudo, vários cooperam, cada um com seu contrato. Ethernet entrega quadros na rede local. IP endereça e encaminha pacotes entre redes. TCP oferece conexão confiável sobre IP. TLS protege a comunicação. HTTP organiza requisições e respostas. OIDC, por cima de HTTP e TLS, organiza autenticação federada e tokens.

  • Conectividade: Ethernet, ARP, IP, ICMP, TCP, UDP e roteamento.
  • Aplicação: DNS, HTTP, SSH, SMTP, APIs e bancos de dados organizam serviços.
  • Segurança e identidade: TLS, mTLS, Kerberos, SAML, OIDC e OAuth criam confiança, identidade e proteção.
  • Plataforma: Kubernetes, service mesh, ingress, API gateway e observabilidade usam protocolos para automatizar comunicação.

Um usuário acessando uma aplicação web pode passar por Wi‑Fi, Ethernet, IP, TCP, TLS, HTTP, DNS, autenticação federada, APIs internas e conexão com banco. Cada trecho pode funcionar ou falhar de forma diferente. Às vezes a rede entrega os bytes perfeitamente, mas a aplicação rejeita a mensagem porque o contrato não foi cumprido.

Erros comuns:
  • Achar que ping funcionando prova que a aplicação funciona. Ping testa ICMP e alcance básico; não valida TCP na porta do serviço, TLS, HTTP, autenticação nem a API.
  • Tratar todo erro 4xx ou 5xx como problema de rede. Esses códigos são respostas do protocolo de aplicação: o servidor recebeu a mensagem e respondeu. Leia os logs da aplicação antes de mexer em firewall e link.
  • Ignorar versão e negociação. Uma atualização de TLS, API ou schema pode fazer cliente e servidor deixarem de se entender. Documente as versões suportadas, as depreciações e os testes de compatibilidade.
